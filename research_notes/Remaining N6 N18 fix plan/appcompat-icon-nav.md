# AppCompat icon loading (srcCompat) and Activity navigation contracts

## app:srcCompat vs android:src: which attribute wins, what TypedArray call resolves the drawable, and what happens when the id is -1/unresolved?

### Takeaway
`android:src` is resolved as a `Drawable` directly off the `TypedArray`, while `app:srcCompat` is resolved as a resource id with a `-1` default meaning "not set"; when both are present the srcCompat drawable is applied last and therefore wins. The repo's `ImageView` currently only reads `android:src` as a raw id and ignores `srcCompat` entirely.

### Cited Findings
- `TypedArray.getDrawable(index)` "retrieves the Drawable for the attribute at the given index" and "throws an exception if the attribute is defined but is not a color or drawable resource"; it returns "Drawable for the attribute, or null if not defined", throwing `RuntimeException` if recycled and `UnsupportedOperationException` if the attribute is defined but is not a color or drawable resource — [TypedArray.getDrawable](https://developer.android.com/reference/android/content/res/TypedArray)
- `TypedArray.getResourceId(index, defValue)` "retrieves the resource identifier for the attribute at index", returning "the resource identifier of the final resource value that was found, not necessarily the original resource that was specified by the attribute", or `defValue` "if the attribute is not defined or not a resource"; throws `RuntimeException` "if the TypedArray has already been recycled" — [TypedArray.getResourceId](https://developer.android.com/reference/android/content/res/TypedArray)
- `android:src` (`R.attr.src`, constant `0x01010119`) "sets a drawable as the content of this ImageView" and "may be a reference to another resource ... or a theme attribute ... [or] a color value" — [R.attr](https://developer.android.com/reference/android/R.attr)
- The repo's `ImageView(Context, AttributeSet, int)` reads only `android:src` via `attrs.getAttributeResourceValue(..., "src", 0)` and calls `setImageResource(src)` when nonzero — `framework/android/widget/ImageView.java` (repo file, read-only)

### Inferences
- The AppCompat pattern (from AndroidX training knowledge, **not** verified against a citable source in this pass) is `AppCompatImageHelper.loadFromAttributes`: obtain the `AppCompatImageView` styleable, read `android_src` with `getDrawable()` and apply it, then read `srcCompat` with `getResourceId(..., -1)` and, when the id is not `-1`, load via `AppCompatResources.getDrawable(context, id)` and apply it — so srcCompat wins by application order, and `-1` means "attribute absent, do nothing".
- Because `getResourceId` resolves through references/theme attributes to the *final* resource value, a srcCompat value of `?attr/...` resolves to the terminal drawable id before the `-1` check.
- Framework-level parity therefore means: resolve `android:src` with the `getDrawable` path (color values included — a plain `#rgb` must also work per `R.attr.src`), resolve `srcCompat` with the `getResourceId(..., -1)` path, skip when `-1`, and apply srcCompat after `android:src`.

### Gaps
- No citable AndroidX source was reachable in this pass (Context7 returned only `developer.android.com` reference pages; the `AppCompat` library-id lookup returned an unrelated demo repo), so the exact `AppCompatImageView` styleable indices, the `hasValue`-vs-`-1` guard form, and tint-attribute (`tint`, `imageTintMode`) handling order could not be confirmed — flag for a follow-up against `androidx.appcompat:appcompat` sources (e.g. `AppCompatImageHelper`, `AppCompatImageView`, `TintTypedArray`).
- Whether AppCompat treats `srcCompat="0"`/unresolved-reference differently from absent (i.e. explicit clear vs no-op) was not confirmable from official docs.

## AppCompatResources.getDrawable: fallback chain (vector, animated, framework) and exception contract on missing resources?

### Takeaway
The only citable contract is the platform one underneath: `Resources`/`Context.getDrawable` throws `Resources.NotFoundException` when the id does not exist (and `0` is an invalid id). The vector/animated-vector backport chain inside `AppCompatResources` could not be verified from official sources in this pass.

### Cited Findings
- `Context.getDrawable(id)`: "returns a drawable object associated with a particular resource ID and styled for the current theme"; "the value 0 is an invalid identifier"; throws `Resources.NotFoundException` "if the given ID does not exist" — [Context.getDrawable](https://developer.android.com/reference/android/content/Context)
- `Resources.getDrawable(id)`: "return a drawable object associated with a particular resource ID. Various types of objects will be returned depending on the underlying resource — for example, a solid color, PNG image, scalable image, etc."; throws `Resources.NotFoundException` "if the given ID does not exist"; deprecated at API 22 in favor of `getDrawable(int, Theme)`, and themed drawables should use `Context.getDrawable(int)` — [Resources.getDrawable](https://developer.android.com/reference/android/content/res/Resources)
- The repo's `Resources.getDrawable(int)` delegates to its resource-table path and its `missing(id)` helper builds a `NotFoundException` ("no resource table: 0x..."); `getDrawable(int, Theme)` delegates to `getDrawable(id)` — `framework/android/content/res/Resources.java` (repo file, read-only)

### Inferences
- Framework-level parity for the FAB-plus-icon case only *requires* the platform contract: unknown id → `NotFoundException` (a `RuntimeException`), never a silent null; id `0` is invalid. The repo's `ImageView` constructor currently swallows `RuntimeException` around `setImageResource`, which diverges from platform behavior where inflation of a bad `android:src` propagates (via `UnsupportedOperationException`/`NotFoundException`) rather than silently clearing.
- Any `AppCompatResources`-equivalent shim in the framework must therefore: attempt vector/animated inflation first (backport path on old platforms), fall back to framework `getDrawable`, and let `NotFoundException` propagate — but the exact delegation order and nullability are **inference**, not sourced.

### Gaps
- No official `AppCompatResources.getDrawable` documentation or AndroidX source was retrieved (no citable page for its null-vs-throw behavior, `ResourceManagerInternal`/`AppCompatDrawableManager` caching, or animated-vector handling). The commonly cited behavior — returns a tinted/cached drawable, `null` only when the resource exists but decodes to nothing, throws `NotFoundException` for unknown ids — is training knowledge and must be re-verified against AndroidX source before implementation.
- Whether `AppCompatResources.getDrawable` wraps/retries with the activity theme vs application context theming could not be confirmed.

## Activity.navigateUpTo / TaskStackBuilder: exact single-intent rule and parent-activity resolution?

### Takeaway
`navigateUpTo` takes exactly one `upIntent`: if that activity already exists in the task history, this and all intervening activities are finished and the intent is delivered (returns `true`); otherwise every activity is finished down to the task root ("in-app home", returns `false`). Parent intents come from the manifest `parentActivityName` chain via `getParentActivityIntent`, and cross-task Up must synthesize the parent stack with `TaskStackBuilder` after consulting `shouldUpRecreateTask`.

### Cited Findings
- `Activity.navigateUpTo(upIntent)`: "navigate from this activity to the activity specified by upIntent, finishing this activity in the process. If the activity indicated by upIntent already exists in the task's history, this activity and all others before the indicated activity in the history stack will be finished"; "if the indicated activity does not appear in the history stack, this will finish each activity in this task until the root activity of the task is reached, resulting in an 'in-app home' behavior"; "returns true if up navigation successfully reached the activity indicated by upIntent and upIntent was delivered to it. false if an instance of the indicated activity could not be found and this activity was simply finished normally"; "should be used when performing up navigation from within the same task as the destination. If up navigation should cross tasks in some cases, see shouldUpRecreateTask(Intent)" — [Activity.navigateUpTo](https://developer.android.com/reference/android/app/Activity)
- `Activity.getParentActivityIntent`: "obtain an Intent that will launch an explicit target activity specified by this activity's logical parent. The logical parent is named in the application's manifest by the parentActivityName attribute. Activity subclasses may override this method to modify the Intent returned by super.getParentActivityIntent() or to implement a different mechanism of retrieving the parent intent entirely" — [Activity.getParentActivityIntent](https://developer.android.com/reference/android/app/Activity)
- `Activity.shouldUpRecreateTask(targetIntent)`: "returns true if the app should recreate the task when navigating 'up' from this activity"; "if this method returns false the app can trivially call navigateUpTo(Intent) ... If this method returns false [sic — docs text; sense: if true], the app should synthesize a new task stack by using TaskStackBuilder" — [Activity.shouldUpRecreateTask](https://developer.android.com/reference/android/app/Activity)
- `TaskStackBuilder.addParentStack(Class)`: "adds the activity parent chain as specified by the parentActivityName attribute of the activity (or activity-alias) element in the application's manifest to the task stack builder" — [TaskStackBuilder.addParentStack](https://developer.android.com/reference/android/app/TaskStackBuilder)
- `TaskStackBuilder.addNextIntentWithParentStack(nextIntent)`: "add a new Intent with the resolved chain of parents for the target activity ... equivalent to calling addParentStack with the resolved ComponentName of nextIntent (if it can be resolved), followed by addNextIntent with nextIntent" — [TaskStackBuilder.addNextIntentWithParentStack](https://developer.android.com/reference/android/app/TaskStackBuilder)
- `Activity.onCreateNavigateUpTaskStack(builder)`: "define the synthetic task stack ... The default implementation ... adds the parent chain of this activity as specified in the manifest"; "invoked by the default implementation of onNavigateUp() if shouldUpRecreateTask(Intent) returns true"; apps wanting extra Intent parameters should override `onPrepareNavigateUpTaskStack(TaskStackBuilder)` — [Activity.onCreateNavigateUpTaskStack](https://developer.android.com/reference/android/app/Activity)
- `Activity.navigateUpToFromChild` is "deprecated in API level 30 — use navigateUpTo(Intent) instead"; "default implementation simply calls navigateUpTo(upIntent) on this activity (the parent)" — [Activity.navigateUpToFromChild](https://developer.android.com/reference/android/app/Activity)
- The repo's `Activity.navigateUpTo` finishes intermediaries when the destination `ComponentName` is already on its navigator stack, else calls `startActivity(upIntent)` then `finish()`; `getParentActivityIntent()` currently returns `null` unconditionally — `framework/android/app/Activity.java` (repo file, read-only)

### Inferences
- The "single-intent rule" flagged in review: Up navigation state is exactly one explicit `Intent` naming the parent (component-resolved, manifest `parentActivityName` chain consulted only to *build* that intent or a synthetic stack — never a multi-intent `startActivities` fan-out, which the repo overrides only as a compatibility loop). `NavUtils.navigateUpTo`/`shouldUpRecreateTask` in the support library implement the same `shouldUpRecreateTask ? synthesize-stack : navigateUpTo` branch.
- Repo parity gaps visible from the cited contract: (a) platform delivers `upIntent` to the reached instance (`onNewIntent` path implied by "upIntent was delivered to it") — the repo's stack-finish path never delivers; (b) the not-found path must finish down to the *root* and return `false` — the repo instead launches the intent and finishes only self, returning `true`; (c) `getParentActivityIntent` must resolve `parentActivityName` from the package manager rather than return null.

### Gaps
- The precise delivery mechanism on the found path (whether the platform uses `FLAG_ACTIVITY_CLEAR_TOP`-equivalent `onNewIntent` delivery vs relaunch) is not spelled out on the reference page; confirm against AOSP `Activity.navigateUpTo` / `Instrumentation` source before reimplementing.
- `NavUtils` (support-library `parentActivityName` + `meta-data android.support.PARENT_ACTIVITY` fallback resolution) has no citable page in this pass; the manifest-only chain above is the platform contract.

## DisplayMetrics density: where must the framework supply it so drawable selection and layout agree?

### Takeaway
Density must be supplied as one mutually consistent snapshot — `density`, `densityDpi`, `scaledDensity`, `xdpi`/`ydpi` — into the `Resources`/`Configuration` the activity inflates and measures with, because both drawable selection (`getDrawableForDensity`, where `0` means "use the configuration density") and dp→px layout scaling read from the same source.

### Cited Findings
- `Resources.getDrawableForDensity(id, density, theme)`: "return a drawable object associated with a particular resource ID for the given screen density in DPI"; "`density`: the desired screen density indicated by the resource as found in DisplayMetrics. A value of 0 means to use the density returned from getConfiguration(). This is equivalent to calling getDrawable(int,Theme)"; throws `NotFoundException` "if the given ID does not exist" — [Resources.getDrawableForDensity](https://developer.android.com/reference/android/content/res/Resources)
- `Configuration.densityDpi`: "the target screen density being rendered to, corresponding to density resource qualifier. Set to DENSITY_DPI_UNDEFINED if no density is specified"; `DENSITY_DPI_UNDEFINED` constant value is `0` — [Configuration.densityDpi](https://developer.android.com/reference/android/content/res/Configuration) / [DENSITY_DPI_UNDEFINED](https://developer.android.com/reference/android/content/res/Configuration)
- `Bitmap.getDensity` default: "the same density as the current display, unless the current application does not support different screen densities in which case it is DisplayMetrics.DENSITY_DEFAULT" — [Bitmap.getDensity](https://developer.android.com/reference/android/graphics/Bitmap)
- The repo already threads one snapshot: `DisplayMetrics` documents the native `int[8]` layout `[w, h, densityDpi, density*1000, scaled*1000, xdpi*1000, ydpi*1000, scale]` with a 160dpi/scale-1 fallback and mutual-consistency fixups (`density<=0 → scale`, `scaledDensity<=0 → density`, `xdpi/ydpi<=0 → densityDpi`) — `framework/android/util/DisplayMetrics.java`; `Resources.setMetrics(...)` copies all fields into the system snapshot, and `Activity.applyMetrics` repolls per frame slice — repo files (read-only)

### Inferences
- The parity requirement is agreement, not just presence: the `Resources` instance backing `getDrawable*` and the metrics backing `TypedValue.applyDimension` / layout must be seeded from the same compositor snapshot (the repo's `setMetrics` + `applyMetrics` shape already does this); a framework that supplies density to one path but not the other gets correctly-chosen drawables at wrong pixel sizes or vice versa.
- `densityDpi` doubles as the resource-qualifier selector, so it must track the bucket the compositor reports (not a hardcoded 160) whenever the window moves across outputs with different scales; `0`/undefined must collapse to the 160 fallback exactly as the repo's `DisplayMetrics` already does.

### Gaps
- The exact pre-Jelly-Bean alias-density quirk ("if the density configuration of the alias resource is different than the actual resource, the density of the returned Drawable would be incorrect... work around with getValue(..., resolveRefs)") — [Resources.getDrawable](https://developer.android.com/reference/android/content/res/Resources) — is documented as fixed since JELLY_BEAN; no modern drawable-selection edge beyond `getDrawableForDensity` semantics was found, so alias-resolution parity needs AOSP `ResourcesImpl` source, not docs.
