# In-process ARM64 execution inside a live x86_64 host process

## Intel Houdini / NDK translation on x86 Chromebooks: runtime in-process DBT, not install-time, not separate-process

### Takeaway
Google/Intel-style ARM-on-x86 translation is runtime dynamic binary translation that runs **inside the app's own (x86) process** via Android's NativeBridge interface: at install the package manager merely prefers an x86 slice when present, and ARM-only `.so` files are translated when loaded. Google still ships a proprietary `libndk_translation.so` in x86_64 ChromeOS images, while Intel's original Houdini survives only in community archives with its documentation deleted.

### Cited Findings
- `libndk_translation` ships under an "ARM-to-AMD DBT Software License" covering `/system/lib/libndk_translation.so` and `/system/lib64/libndk_translation.so` — DBT means on-device runtime translation, and vendor images contain only the runtime plus guest `arm/` libs, no AOT compiler tooling — [DBT license](https://raw.githubusercontent.com/supremegamers/vendor_google_proprietary_ndk_translation-prebuilt/chromeos_zork/ARM_TO_AMD_DBT_LICENSE.txt); [Intel Houdini vendor image layout](https://github.com/Electry/android-x86-vendor-intel-houdini)
- AOSP's NativeBridge README states a bridge "enables apps with native components to run on systems with different ISA or ABI" and that AOSP itself "does not provide an actual native bridge" — translation is a loadable third-party runtime, with no install-time ARM-to-x86 compiler anywhere in the flow — [AOSP libnativebridge README](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/README.md)
- Confirmed in-process: libnativebridge "handles loading of native libraries with a foreign ISA… into a managed JVM process using the native ISA in the host environment," with "a separate linker, which typically uses a different linker config than the host one" for the guest libs — the app process is x86/ART and ARM code is translated inside that same process — [AOSP libnativebridge README](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/README.md)
- Execution flow is per-library, not per-process: `System.loadLibrary` on an ARM lib fails on the host linker, then `NB::Available?` → `nb: load library` → per-JNI-method `nb: get method trampoline`; the whole app is never "run translated" as a separate process — [AOSP native-bridge startup diagram](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/nb-diagram.png)
- At fork, when `app_isa != runtime_isa`, the runtime pre-initializes the bridge and mounts a fake `/proc/cpuinfo` plus `CPU_ABI(2)`/`SUPPORTED_ABIS` env so the app sees a consistent guest ABI — [AOSP native-bridge startup diagram](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/nb-diagram.png)
- The bridge is discovered by `dlopen` plus lookup of the `NativeBridgeItf` symbol, configured by system properties `ro.dalvik.vm.native.bridge=libndk_translation.so`, `ro.dalvik.vm.isa.arm=x86`, `ro.dalvik.vm.isa.arm64=x86_64` — [startup diagram](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/nb-diagram.png); [libndk_translation makefile](https://raw.githubusercontent.com/supremegamers/vendor_google_proprietary_ndk_translation-prebuilt/chromeos_zork/libndk_translation.mk)
- The interface is versioned (v7+): `initialize`, `loadLibrary`, `isSupported`, `getTrampolineWithJNICallType` (replacing `getTrampoline`), namespaces, `unloadLibrary`, plus `getSignalHandler` — ART chains the bridge's SIGSEGV handler after its own, confirming signals are a first-class bridge concern — [native_bridge.h](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/include/nativebridge/native_bridge.h)
- Reverse direction: ART passes `NativeBridgeRuntimeCallbacks` (`getMethodShorty`, `getNativeMethodCount/Methods`) so the bridge builds correctly-typed trampolines per JNI method — [native_bridge.h](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/include/nativebridge/native_bridge.h)
- Google ships `libndk_translation.so` ("version 0.2.3" in the referenced build) inside ChromeOS Android images; the working prebuilt was extracted from a ChromeOS "zork" (AMD) device — i.e. x86 Chromebooks run an x86 Android guest with Google's translator as the fallback for ARM-only NDK libs — [ndk_translation prebuilt README](https://raw.githubusercontent.com/supremegamers/vendor_google_proprietary_ndk_translation-prebuilt/chromeos_zork/README.md)
- x86 slices are preferred when present: the package manager "extracts the best machine code from the package at installation time" using primary/secondary ABIs, and the startup flow gates multilib APKs on "is abi supported?" — translation is the fallback for ARM-only apps — [NDK ABI guide](https://developer.android.com/ndk/guides/abis); [startup diagram](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/nb-diagram.png)
- Still alive in practice: the ndk_translation prebuilt repo was pushed 2025-05-28; BlissRoms-x86 carries a commit "Support a new libndk_translation repo"; Android-x86 9.0-r1 notes "Support arm arch apps via the native bridge mechanism… (64-bit only)" — [BlissRoms-x86 commit](https://github.com/BlissRoms-x86/platform_device_generic_x86_64/commit/b118534ddce65b124f3c458e536b85beccf3a669); [Android-x86 9.0-r1 notes](https://www.android-x86.org/releases/releasenote-9-0-r1.html)
- Intel's own documentation is gone: the Intel support article now redirects to the generic support homepage, the old Android-x86 Houdini how-to is 404, and Intel's projectceladon org has zero Houdini repos — old Intel-Houdini binaries circulate only via community archives — [dead how-to URL](https://www.android-x86.org/documentation/how-to-use-houdini/); [community archive](https://github.com/Electry/android-x86-vendor-intel-houdini)
- No Wikipedia article on Intel Houdini exists — `Houdini_(software)` is the SideFX 3D-animation package — [Wikipedia](https://en.wikipedia.org/wiki/Houdini_(software))

### Inferences
- Houdini/ndk_translation is the existence proof that in-process ARM→x86 translation of JNI libraries works at product scale — but it is proprietary, undocumented, and inseparable from Android's ART/Zygote process model, so it cannot be lifted into Isakai's runner.
- Guest ARM syscalls must be remapped to host x86 syscall numbers inside the translator since execution stays in-process under the host kernel — but no fetched page documents Houdini/ndk_translation's exact syscall handling, so this is inferred, not sourced.

### Gaps
- No public ChromeOS doc describes ARCVM↔translator internals; chromiumos/docs has no accessible mirror and the ARC pages say nothing about ARM translation.
- The official 16 KB page-size guide mandates ELF `max-page-size=16384` alignment with Play enforcement for Android 15+ targets but never mentions Houdini/NDK translation — how the translator handles 16 KB-aligned guests is unknown — [page-size guide](https://developer.android.com/guide/practices/page-sizes)
- "Intel discontinuation" rumors are plausible given the removed article and absent Celadon integration, but zero citable 2025–2026 sources confirm or deny Houdini support status.

## Open in-process AArch64-to-x86_64 DBT engines: only Unicorn ships; all else is whole-process, same-arch, wrong-direction, or prototype

### Takeaway
For "x86_64 process loads an ARM64 library and calls its functions," Unicorn is the only open, shipping, embeddable answer — and it is CPU-only, so the loader, ABI glue, TLS, and syscalls are your work. QEMU is whole-process only, QBDI/Frida are same-ISA-only, and Box64/FEX/Prism/Rosetta are the wrong direction or whole-process.

### Cited Findings
- QEMU user-mode's CLI is `qemu-<guest> program [args]` — the entire host process *is* the guest; there is no "load ARM .so into an x86_64 process" mode — [QEMU user docs](https://www.qemu.org/docs/master/user/main.html)
- TCG supports Arm/AArch64 and x86_64 guests on any host in system and user mode, but always as a separate emulated process/VM — [QEMU emulation overview](https://www.qemu.org/docs/master/about/emulation.html)
- TCG plugins are explicitly observation-only instrumentation hooks, not a way to execute guest code inside your own process — [QEMU TCG plugin docs](https://www.qemu.org/docs/master/devel/tcg-plugins.html)
- QBDI recompiles the *original program's own* code where "host" vs "guest" means instrumentation context vs instrumented program — the same ISA in one process sharing heap/libs; architecture support is per-target builds (build for the machine you instrument), not ARM→x86 translation — [QBDI intro](https://qbdi.readthedocs.io/en/stable/intro.html); [QBDI arch support](https://qbdi.readthedocs.io/en/stable/architecture_support.html)
- Frida Gum is a "cross-platform [OS] instrumentation library in C" — cross-OS, not cross-ISA; Stalker has separate per-architecture implementations and follows/rewrites native threads, never executing a foreign ISA — [Frida Gum docs](https://frida.re/docs/gum/); [Frida Stalker docs](https://frida.re/docs/stalker/); [Frida README](https://raw.githubusercontent.com/frida/frida/main/README.md)
- Unicorn is a QEMU-TCG-based "lightweight, multi-architecture CPU emulator framework" in pure C with many language bindings, covering ARM64 and x86(-64); latest release 2.1.4 (2025-09-09) — status: shipping product — [Unicorn README](https://raw.githubusercontent.com/unicorn-engine/unicorn/master/README.md); [Unicorn site](https://www.unicorn-engine.org/)
- Unicorn's API is exactly in-process: `uc_open(UC_ARCH_ARM64,…)`, `uc_mem_map`, `uc_mem_write`, `uc_hook_add`, `uc_emu_start`, `uc_reg_read/write` — guest code plus host callbacks live in the host process, per its ARM64 sample — [sample_arm64.c](https://raw.githubusercontent.com/unicorn-engine/unicorn/master/samples/sample_arm64.c)
- Unicorn caveats: CPU-only (memory, syscalls, ABI linkage to real `.so` exports are modeled by the embedder), GPLv2, JIT performance below native, community-maintained — [Unicorn README](https://raw.githubusercontent.com/unicorn-engine/unicorn/master/README.md)
- Box64 "enables running x86_64 Linux programs… on non-x86_64 Linux systems such as Arm" — x86-on-Arm, wrong direction — [Box64 README](https://raw.githubusercontent.com/ptitSeb/box64/main/README.md)
- FEX "Emulate[s] x86 Programs on ARM64… run x86 applications on ARM64 Linux devices" — x86-on-Arm, wrong direction — [FEX README](https://raw.githubusercontent.com/FEX-Emu/FEX/main/Readme.md); [FEX site](https://fex-emu.com/)
- Rosetta 2 is whole-process x86_64-on-arm64, Apple-only and closed; the system "launches the translated executable in place of the original" — [Apple Rosetta docs](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment.md)
- Microsoft Prism: "x86 and x64 apps run under emulation on Arm devices" — wrong direction, closed, OS-level — [Windows on Arm overview](https://learn.microsoft.com/en-us/windows/arm/overview); [x86 emulation docs](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)
- Popcorn Linux (heterogeneous-ISA systems software) spans kernels/ISAs with thread migration, not two ISAs executing in one address space — research prototype — [Popcorn Linux](https://popcornlinux.org/)

### Inferences
- Nobody ships an open library that takes an ARM64 `.so` plus a set of host callbacks and runs the `.so`'s functions in-process on x86_64; every open path (Unicorn embedding, forking TCG) requires building the loader/ABI layer.
- FEX's thunking model (forwarding GL/Vulkan calls to host libraries) is the attractive template for game libraries, but it exists only in the x86-guest direction; no ARM-guest equivalent exists on x86_64 hosts.

### Gaps
- "libtcg / TCG-as-a-library / library compartmentalization": no shipping artifact found; search endpoints served bot-challenges from this network, so mailing-list proposals could not be verified — at best research discussion, not a product.
- ARMore / "compound ISA" / mixed-ISA single-address-space claims unverified (candidate repo URLs 404'd, arXiv query returned noise); a proper scholar search for "heterogeneous-ISA migration" and "cross-ISA DBT" is still owed.
- Intel Bridge Technology (Android-on-Alder Lake): no fetchable citable line; treat as dead end — direction was Arm-apps-on-x86, not in-process library execution.

## Why in-process is harder than whole-process: one thread must serve two live ABIs at every crossing

### Takeaway
Whole-process emulation (qemu-user) owns the process — one guest CPU state, one signal namespace, one TLS ABI — and converts only at the syscall boundary. In-process translation must multiplex two live ABIs onto one register file, one stack, one TLS register, and one signal table, paying a state-sync cost on every guest↔host call.

### Cited Findings
- Natively the kernel delivers `sa_sigaction(int, siginfo_t*, ucontext_t*)` with the fault PC in `ucontext.mcontext` so a handler resumes exactly there — [sigaction docs](https://man7.org/linux/man-pages/man2/sigaction.2.html)
- qemu-user rewrites signal delivery wholesale (`host_to_target_signal`, `queue_signal`, `force_sig_fault`, guest `rt_frame` construction); a synchronous SIGSEGV/SIGILL from a translation block must map the host fault PC back to the guest PC via TB lookup before queueing — [QEMU linux-user signal.c](https://raw.githubusercontent.com/qemu/qemu/master/linux-user/signal.c)
- In-process, a fault inside translated guest code presents a *host* PC to the kernel, so the translator must intercept first and recover guest state; async signals are worse because the thread may be in guest code, in a thunk, or in host code, each needing different mask/context treatment — QEMU's own code does an explicit block-process-restore dance (`block_host_signals`) — [QEMU linux-user signal.c](https://raw.githubusercontent.com/qemu/qemu/master/linux-user/signal.c)
- `sigaltstack()` (`ss_sp`/`SS_ONSTACK`) is per-thread with a single stack; guest and host both want alt-stack semantics, and a signal landing on the wrong alt-stack corrupts the other ABI's frames — qemu-user emulates this with `target_save_altstack`/`target_restore_altstack` in guest state, with no in-process competitor — [sigaltstack docs](https://man7.org/linux/man-pages/man2/sigaltstack.2.html); [QEMU linux-user signal.c](https://raw.githubusercontent.com/qemu/qemu/master/linux-user/signal.c)
- The x86_64 thread pointer lives in FS (set via `arch_prctl(ARCH_SET_FS)`), while ARM64 uses TPIDR_EL0 — one thread has one register set, but guest libc and host libc each expect their own thread-control block, so every crossing must swap the thread pointer or rewrite all guest TLS accesses — [x86 FSGS docs](https://docs.kernel.org/arch/x86/x86_64/fsgs.html); [arch_prctl docs](https://man7.org/linux/man-pages/man2/arch_prctl.2.html)
- `clone()` sets TLS at thread birth via `CLONE_SETTLS`; a host-created thread entering guest code has host TLS but no guest TCB, while a guest-created thread needs host TLS *and* guest TLS plus emulated TID/PID mapping and a signal queue — both creators must be hooked — [clone docs](https://man7.org/linux/man-pages/man2/clone.2.html)
- QEMU's MTTCG design assumes translator-owned threads with global-lock/exclusive-TB discipline, a discipline an in-process engine cannot impose on a host that owns the scheduler — [QEMU MTTCG docs](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html)
- Translated frames are not native frames: DWARF `.eh_frame` describes host code only, and qemu-user documents its own `gdbstub`/signal virtualization instead of native unwinding — interleaving real host frames with JITted guest frames on one stack leaves neither unwinder understanding both — [QEMU user docs](https://www.qemu.org/docs/master/user/main.html)
- Calling conventions collide directly: SysV AMD64 passes the first 6 integer args in `RDI,RSI,RDX,RCX,R8,R9` (+XMM0–7), while AAPCS64 uses `x0–x7` plus NEON regs with 16-byte SP alignment — every guest→host call needs a thunk that spills guest regs, reshuffles args, switches stack/TLS/signal mask, calls, then marshals the return — [x86 conventions](https://en.wikipedia.org/wiki/X86_calling_conventions); [calling conventions](https://en.wikipedia.org/wiki/Calling_convention)
- Return addresses pushed on a host stack are host PCs, meaningless to guest backtraces and exception handlers — guest-return translation (shadow stack) is required; whole-process qemu-user instead converts only at the syscall boundary — [QEMU user docs](https://www.qemu.org/docs/master/user/main.html)
- Measured anchor: Box64 states its DynaRec "achieves a speed boost 5–10x faster than the interpreter alone" — [Box64 project page](https://github.com/ptitSeb/box64)
- FEX reduces overhead by forwarding API calls to host GL/Vulkan libraries, offers a per-app toggle "skipping costly memory model emulation," and ships an experimental code cache "to minimize stuttering" — [FEX README](https://raw.githubusercontent.com/FEX-Emu/FEX/main/Readme.md); [FEX site](https://fex-emu.com/)
- x86 is strongly ordered (~TSO) while ARM64 is weakly ordered, so a translator for the reverse direction must insert barriers or run a "strong memory mode" (Box64 exposes `DYNAREC_STRONGMEM=1`) — [kernel memory-barrier docs](https://www.kernel.org/doc/Documentation/memory-barriers.txt); [memory ordering](https://en.wikipedia.org/wiki/Memory_ordering); [Box64 project page](https://github.com/ptitSeb/box64)
- Microsoft documents per-module emulator caches for Prism but gives no percentage; no authoritative single "QEMU TCG slowdown factor" or "Houdini overhead %" was found in any fetched page — commonly quoted 5–10x figures for TCG are folklore, not measured here — [x86 emulation docs](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation); [QEMU emulation overview](https://www.qemu.org/docs/master/about/emulation.html)

### Inferences
- Per-crossing cost model: save guest CPU state + spill regs + swap TLS base + block/merge signal masks + marshal args + memory fence + TB-validity check on return — none of which exists for a native call, so JNI-heavy game libraries (hundreds of crossings per frame) pay thunk overhead even when the translated body itself is fast.
- SSE↔NEON has no exact mapping for shuffles, horizontal ops, and FP edge cases (NaN/exception/rounding), forcing slow scalar fallbacks — general claim, no single fetched spec page proves the full mapping table.
- Self-modifying/JITted guest code (Unity IL2CPP output, guest JITs) is the expected performance cliff: guest JIT emits ARM code the translator must re-translate, with page-invalidation churn on top — which is exactly what FEX's and Prism's code caches exist to amortize.

### Gaps
- No published per-thunk nanosecond cost for Houdini, Box64, or FEX; treat any cited figure as an estimate.
- No fetched page documents Apple/Intel's exact guest-PC recovery or TLS-swap sequence — inferred from kernel plus QEMU mechanics.

## Minimal version cost: translating only Isakai's small game-logic .so files with host callbacks is feasible but means building a DBT engine, not integrating one

### Takeaway
Constraining translation to small game-logic `.so` files with all OS interaction via host callbacks removes the hardest problems (guest syscalls, guest libc, guest GPU drivers) but still requires a new engine covering loader, translator, TLS, signals, and per-call thunks — Unicorn supplies only the CPU core, so the build is measured in months of specialist work, not an integration sprint.

### Cited Findings
- Unicorn's embeddable API (`uc_open`/`uc_mem_map`/`uc_emu_start`/hooks) already supports the "translated code calls back into host functions" shape via hook callbacks in the host process — but memory, syscalls, and ABI linkage to real `.so` exports must be modeled by the embedder — [sample_arm64.c](https://raw.githubusercontent.com/unicorn-engine/unicorn/master/samples/sample_arm64.c); [Unicorn README](https://raw.githubusercontent.com/unicorn-engine/unicorn/master/README.md)
- The NativeBridge design validates the callback-thunk architecture: per-JNI-method trampolines built from ART's `getMethodShorty` type info, with a separate linker config for guest libs — i.e. the shipping product for this exact problem translates only app `.so` code and crosses into the host runtime per method — [native_bridge.h](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/include/nativebridge/native_bridge.h); [AOSP libnativebridge README](https://raw.githubusercontent.com/LineageOS/android_art/lineage-22.2/libnativebridge/README.md)
- The per-crossing mechanism inventory (TLS swap, signal-mask dance, register reshuffle, guest-PC recovery) is the scope floor: each item above is a subsystem even before translating a single instruction — [QEMU linux-user signal.c](https://raw.githubusercontent.com/qemu/qemu/master/linux-user/signal.c); [x86 FSGS docs](https://docs.kernel.org/arch/x86/x86_64/fsgs.html)
- FEX's precedent shows the highest-leverage optimization is forwarding API calls to host libraries rather than translating them — the direct analogue of "all OS interaction via callbacks into the host" — [FEX README](https://raw.githubusercontent.com/FEX-Emu/FEX/main/Readme.md)
- No open project publishes per-thunk costs or a drop-in ARM64→x86_64 in-process translator with loader, TLS, and signal support — that assembly simply does not exist as a shippable component — see Gaps in all sections above.

### Inferences
- A minimal build decomposes into: (1) ELF loader for the ARM64 `.so` (relocations, `R_AARCH64_*`, dependency scoping like NativeBridge's separate linker config); (2) AArch64→x86_64 translator core (Unicorn embedding or a fresh dynarec — the single largest block); (3) per-export thunk generator mapping AAPCS64 to SysV AMD64 with TLS swap and signal masking; (4) host-callback table replacing guest syscalls/libc (game logic that is pure compute needs almost none; anything touching time/threads/files needs each entry hand-written); (5) fault/signal interposition for guest-PC recovery.
- Scoping to "small game-logic" files is what makes this tractable at all: pure-compute code needs only (1)–(3), avoids the memory-model and SIMD cliffs (game logic is rarely NEON-saturated or ordering-sensitive), and sidesteps GPU forwarding entirely since rendering stays host-side.
- Rough sizing, estimated not sourced: a Unicorn-based prototype running one pure-compute `.so` with hand-written thunks is a multi-week specialist spike; production-hardening (signals, TLS for guest-created threads, unwinding, 16 KB-page guests, JITted guest code) is what turns it into multi-month engine work with no off-the-shelf core beyond Unicorn's CPU emulation. The plan's standing rule — ARM code never executes on x86 silicon, each host runs its native slice — remains the cheaper strategy until a motivating ARM-only game justifies this build.
- The 16 KB-page mandate is a latent trap for any such engine: Android 15+ guests increasingly assume 16 KB granularity, and QEMU's removal of its page-size-pretend flag shows there is no cheap knob — any in-process engine must decide its page-granularity story up front.

### Gaps
- No citable estimate exists for building an ARM64→x86_64 in-process translator; the sizing above is inference from subsystem count, not a sourced figure.
- Whether small game-logic `.so` files in practice avoid syscalls/threads/TLS enough to skip subsystems (4)–(5) can only be settled by surveying the actual motivating binaries (`nm -D`, syscall inventory) — no such survey was in scope here.
