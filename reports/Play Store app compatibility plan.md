# Drive every runnable Play app to green

The full path from today's four green pinned apps to every runnable Play Store app runs through six sequenced phases gated by motivating apps plus named owners, with each phase exited only when its pinned set holds top grade across two consecutive runs. The central finding is that nearly all broad compatibility comes from completing shared subsystems in dependency order rather than fixing apps one by one, because every project that runs arbitrary Play apps ships a full Android userspace while API reimplementation covers only the Google-services slice on top of an already-complete system ([Waydroid docs](https://docs.waydro.id/)) ([microG GmsCore wiki](https://github.com/microg/GmsCore/wiki)). That fact sets the program shape: Isakai keeps its image-free JVM-runner architecture but must still deliver the same contract depth a full system provides, starting from the proven offline-utility base, compounding through storage, media, networked, Play-services, and native-game phases, and stopping at an explicit ceiling where uncertified builds cannot follow. The ceiling is institutional rather than technical, since Google-signed builds carry Play Integrity verdicts, Widevine L1, and licensed translation stacks an independent host cannot replicate, and the visible boundary is Waydroid's own uncertified-device self-registration flow which restores Play Services access without restoring certified verdicts ([Waydroid Play certification FAQ](https://docs.waydro.id/faq/google-play-certification)). Runnable therefore means everything except apps that hard-gate on `MEETS_DEVICE_INTEGRITY` or `MEETS_STRONG_INTEGRITY`, hardware DRM, or privileged Play functions, a scope that still covers the bulk of installs in casual games plus utilities.

## Pinned corpus plus fixed grades turns anecdotes into progress

The program measures a funnel rather than a pile of fixed bugs, extending the existing pinned-app flows with screenshots, logs, and exit status into four recorded stages per corpus entry: install rate, launch rate, flow-complete rate, and regression rate. The model is mature practice elsewhere: Steam Deck grades every title Verified, Playable, Unsupported, or Unknown and moves titles upward between fixed tiers as platform features unblock them ([Source](https://www.steamdeck.com/en/verified)), while ProtonDB grades on a fixed medal ladder from platinum down to borked alongside native-client and Deck-Verified dimensions ([Source](https://www.protondb.com/)). A title earns Deck Verified only by passing four fixed boxes covering input, display at default resolution with legible text, seamlessness, and system support for the game plus all its middleware including anti-cheat ([Source](https://www.steamdeck.com/en/verified)), and that last box states the shared-contract rule the plan adopts: middleware-level support is the gate, not title-level accommodation. Proton encodes the same discipline in its tracker, where whitelisted games form the corpus, community nomination queues feed it, and subsystem labels for audio, graphics, drivers, and middleware carry the actual work ([Source](https://github.com/ValveSoftware/Proton/labels). Waydroid's mandatory structured bug template shows the evidence standard that makes the funnel trustworthy, demanding version, device class, OS, kernel, desktop, GPU, plus attached logs and config so every per-app report arrives clusterable to a subsystem ([Source](https://github.com/waydroid/waydroid/blob/main/.github/ISSUE_TEMPLATE/bug_report.yml)).

Failure taxonomy separates one-fix-many-apps work from app-specific noise by recording the symptom at the app and root-causing at the subsystem, with layers running from install and launch through render, input, media and sensors, platform services, and native ABI. Proton's changelog demonstrates the pattern empirically because entries read per-game while fixes land in shared video, font, input, monitor, and driver code ([Source](https://github.com/ValveSoftware/Proton/wiki/Changelog)), and its few title-specific accommodations live as data such as per-window-class automation rules rather than branched runtime code ([Source](https://github.com/ValveSoftware/Proton)). Recent Waydroid issues cluster identically, with per-app symptoms like RenderThread crashes, black video with audio, camera crashes, and translator hangs rooting in shared gralloc, media-manifest, translator, and composer subsystems ([Source](https://github.com/waydroid/waydroid/issues)). The plan therefore permits accommodations only as data in pins, config, and environment, never as branched runtime code, and a reported failure counts as shared-contract only when two pinned apps from different authors hit the same layer and reproduces on a vanilla retest without per-title custom builds, mirroring Proton's retest rule ([Source](https://github.com/ValveSoftware/Proton/labels)). Contract-first depth comes from Android's own Compatibility Test Suite as the runnable versioned corpus model ([Source](https://source.android.com/docs/compatibility/cts)), Firebase Test Lab's Robo crawlers as the automation model for the top of the funnel ([Source](https://firebase.google.com/docs/test-lab)), and ChromeOS's ARC test plan for the manual middle automation misses around state persistence, resize, input parity, and sensor absence ([Source](https://developer.android.com/topic/arc)).

## Faithful runtime and GPU first unlocks games before services do

Graphics and runtime fidelity form the hardest shared work and therefore precede the Play-services push, because engines standardize on a narrow API set served by shippable open components while the binding constraint remains a real host Vulkan driver. Unity supports Android 8.0 plus with Vulkan and OpenGL ES 3.1 and 3.2 while dropping older GLES versions ([Source](https://docs.unity3d.com/Manual/android-requirements-and-compatibility.html)), and Unreal requires 64-bit Arm on Android 8 plus with OpenGL ES 3.2 and Vulkan 1.1 on compatible drivers ([Source](https://dev.epicgames.com/documentation/en-us/unreal-engine/android-development-requirements-for-unreal-engine)). ANGLE translates OpenGL ES 2.0 through 3.1 to Vulkan, desktop GL, GLES, and Direct3D with ES 3.2 conformance passed on the Vulkan backend ([Source](https://angleproject.org/)), Mesa Venus forwards guest Vulkan to host Vulkan over virtio-GPU with explicit host requirements including Vulkan 1.1 plus external-memory file descriptors ([Source](https://docs.mesa3d.org/drivers/venus.html)), Mesa Zink exposes desktop OpenGL on Vulkan-only devices starting from OpenGL 2.1 gated on host features ([Source](https://docs.mesa3d.org/drivers/zink.html)), and gfxstream provides Google's guest-to-host streaming mechanism used by emulator-class virtualized Android ([Source](https://github.com/google/gfxstream)). Serving GLES 3.2 plus Vulkan 1.1 faithfully therefore covers both Unity's minimum and Unreal's declared APIs, with GPU-name allowlists in old games the residual risk. Clear-content media follows the same reimplementation logic because ExoPlayer needs only a MediaCodec-shaped API for its full clear matrix of audio, video, DASH, SmoothStreaming, and HLS including AES-128 at API 23 plus HDR at API 24 ([Source](https://developer.android.com/media/media3/exoplayer/supported-devices)), defaults to platform decoders with optional software extensions for AV1, VP9, FLAC, Opus, and FFmpeg that must be built in ([Source](https://developer.android.com/media/media3/exoplayer/supported-formats)), and supports live and on-demand RTSP ([Source](https://developer.android.com/media/media3/exoplayer/rtsp)). Protected playback is the explicit boundary because ExoPlayer routes it through the MediaDrm API with Widevine cenc at API 19 and cbcs at API 25 ([Source](https://developer.android.com/media/media3/exoplayer/drm)), while new-device Widevine integration follows a certification process with robustness review per device and chipset ([Source](https://www.widevine.com/solutions/widevine-drm)). The runner therefore reimplements MediaCodec over host codecs, stubs MediaDrm as unavailable outside ClearKey, and treats social apps as codec and camera performance risk while subscription video stays behind the certified-only wall.

Bytecode and native execution decide whether that media and graphics work ever runs, with JNI fidelity the top translation risk ahead of hidden-API behavior, invoke-custom mapping, obfuscation artifacts, and multidex ordering. DEX caps invocable method references per file at the 64K limit with multidex default-on only at minSdkVersion 21 and above, otherwise requiring the support library plus attach-time install with secondary-dex lookup through a special class loader ([Source](https://developer.android.com/studio/build/multidex)). The format natively carries method-handle lists, call-site identifiers, and bootstrap-linker handles returning call sites, making invoke-custom a format-level feature a translator must honor ([Source](https://source.android.com/docs/core/dalvik/dex-format)). Android gates hidden APIs through blocklists plus conditionally blocked lists keyed to target SDK, with manufacturers allowed to add but never remove entries ([Source](https://developer.android.com/distribute/best-practices/develop/restrictions-non-sdk-interfaces)), and JNI demands up-front RegisterNatives from JNI_OnLoad with explicit registration strictly required on Android 12 plus, Modified UTF-8 string semantics distinct from UTF-16 accessors, and constrained @FastNative and @CriticalNative behavior ([Source](https://developer.android.com/training/articles/perf-jni)). The ABI story sharpens the sequencing because Play's 64-bit requirement centers on arm64-v8a with x86_64 alongside 32-bit slices ([Source](https://developer.android.com/google/play/requirements/64-bit)), Unreal requires 64-bit Arm and supports both 4 KB and 16 KB page sizes ([Source](https://dev.epicgames.com/documentation/en-us/unreal-engine/android-development-requirements-for-unreal-engine)), and apps targeting API 35 plus must support 16 KB pages with aligned LOAD segments following Android 15's page-size change ([Source](https://developer.android.com/guide/practices/page-sizes)). Google Play already requires new apps and updates to target API 35 since August 2025 ([Source](https://dev.epicgames.com/documentation/en-us/unreal-engine/android-development-requirements-for-unreal-engine)), so any .so the runner loads must honor 16 KB alignment and the runner should prefer x86_64 slices where fat APKs carry them while documenting ARM-only native games as unsupported without emulation.

## Play Services is a ceiling to declare, not a milestone to chase

GMS presence unlocks the largest single block of apps after the framework itself, yet the plan treats attestation as a declared exclusion because no uncertified host passes server-side verdicts durably. Exposure is broad but routinely overstated since embedding a tracker SDK differs from crashing without services, with Firebase Analytics present in about **59%** of analyzed apps ([Exodus Privacy](https://reports.exodus-privacy.eu.org/trackers/49)), AdMob in about **43%** ([Exodus Privacy](https://reports.exodus-privacy.eu.org/trackers/312)), and Crashlytics in about **36%** ([Exodus Privacy](https://reports.exodus-privacy.eu.org/trackers/27)). GMS architecture pairs a lightweight client library in the app with the full implementation in the independently updated system Play services app ([Google](https://developers.google.com/android/guides/overview)), devices without the Play Store simply lack Play services, and Google mandates checking service availability before calling Google APIs ([Google](https://developers.google.com/android/guides/setup)). Without services, FCM token delivery fails and push stops ([Firebase](https://firebase.google.com/docs/cloud-messaging/android/client)), Sign in with Google must fall back to other auth ([Firebase](https://firebase.google.com/docs/auth/android/google-signin)), location, maps, ads, and ads-identifier carry documented runtime dependencies ([Google](https://developers.google.com/android/guides/setup)), AdMob demands manifest App ID plus launch-time initialization ([Google](https://developers.google.com/admob/android/quick-start)), paid and subscription apps must use Play Billing with narrow exceptions ([Google](https://support.google.com/googleplay/android-developer/answer/9858738)), and Play Integrity verdicts split between hard gates that refuse to run and softer degradation ([Google](https://developer.android.com/google/play/integrity)). Categories most likely to hard-fail are banking behind integrity gates, single-login Google-auth apps, license-checked paid apps, and FCM-core messaging and ride-share flows.

MicroG at its September 2026 stable release covers the utility tier but not the gated tier, which is exactly why the plan sequences Play-services apps after media and networked phases rather than first. Latest stable v0.3.17.252432 shipped late September 2026 alongside a parallel patch ([GitHub API](https://api.github.com/repos/microg/GmsCore/releases/latest)), with FCM and fused location rated Full ([microG wiki](https://github.com/microg/GmsCore/wiki/Implementation-status)), Maps v1 Full and Maps v2 Mostly on the Mapbox build ([microG wiki](https://github.com/microg/GmsCore/wiki/Implementation-status)), and push needing no Google account over a persistent connection with daily registration ([microG wiki](https://github.com/microg/GmsCore/wiki/Helpful-Information)). Account auth and Firebase Auth remain Partial with Google sign-in unsupported ([microG wiki](https://github.com/microg/GmsCore/wiki/Implementation-status)), billing receives continuous fixes yet keeps open failures ([microG releases](https://github.com/microg/GmsCore/releases/tag/v0.3.17.252432)), analytics and ads are deliberately unimplemented ([microG wiki](https://github.com/microg/GmsCore/wiki/Implementation-status)), and whole families including Auto, Fitness, Fonts, Geofencing, In-app updates, Wearable, and Nearby carry no support ([microG wiki](https://github.com/microg/GmsCore/wiki/Implementation-status)). The integrity row must be read skeptically because the wiki's Mostly rating is contradicted by open issues reporting Standard Integrity nonfunctional with Classic-only checks ([GmsCore issue #2856](https://github.com/microg/GmsCore/issues/2856)), broken integrity with API errors ([GmsCore issue #2855](https://github.com/microg/GmsCore/issues/2855)), and dead SafetyNet servers ([GmsCore issue #3034](https://github.com/microg/GmsCore/issues/3034)), while the multi-step DroidGuard fix remains unverified ([GmsCore issue #2851](https://github.com/microg/GmsCore/issues/2851). Genuine GMS is unavailable by construction because shipping it requires an Android-compatible build passing the Compatibility Definition Document plus CTS, then a proprietary license and Play Protect certification ([AOSP](https://source.android.com/docs/compatibility/overview)), only certified devices may include Google apps with the Play Store ([Google](https://support.google.com/googleplay/answer/7165974)), and default device integrity on Android 13 plus demands hardware-backed locked bootloader with certified manufacturer image ([Google](https://developer.android.com/google/play/integrity/verdicts)). GrapheneOS sandboxed Play therefore defines the realistic ceiling by running official Play binaries as unprivileged per-profile apps with near-complete compatibility including modular components and store flows ([GrapheneOS](https://grapheneos.org/usage#sandboxed-google-play)), while inherently privileged functions, Auto extensions, and integrity-gated verdicts stay out ([GrapheneOS](https://grapheneos.org/usage#sandboxed-google-play-limitations)). Engine exports inherit the same split because Unity routes billing through Play Console product IDs and test tracks ([Unity](https://docs.unity3d.com/Packages/com.unity.purchasing@4.9/manual/UnityIAPGoogleConfiguration.html)), Unreal routes billing plus achievements through its Google Play online subsystem ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/online-subsystem-googleplay)), Godot vanilla export carries no Play Billing, achievements, AdMob, or Firebase with all of it arriving only via third-party plugins ([Godot](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)), and many Play games depend on Play Games being installed ([GrapheneOS](https://grapheneos.org/usage#sandboxed-google-play)).

## Six phases from proven utilities to native games, each gated and proven

The sequenced program compounds subsystem depth so later categories reuse earlier fixes, with every phase entered only by a small pinned set plus a named owner and exited only on recorded grades. The base already exists in offline utilities with calculator, notes, and puzzle flows green, matching the dependency-depth ordering visible in Deck's input-plus-display before seamlessness before middleware ([Source](https://www.steamdeck.com/en/verified)), ChromeOS ARC guidance from windowing through input parity to sensor handling ([Source](https://developer.android.com/topic/arc)), Waydroid's backlog from compositor and lifecycle foundations to the media, camera, and translation tail ([Source](https://github.com/waydroid/waydroid/issues)), and Proton's arc from years of graphics, audio, input, and middleware work to the still-gated anti-cheat frontier ([Source](https://github.com/ValveSoftware/Proton/wiki/Changelog)).

### Offline utilities are done and form the compounding base

This phase is complete with the current pinned utilities plus the native-ABI Puzzles target already proven, and it stays as the regression anchor every later phase must keep green. Entry required only the existing pins, and proof is the current evidence standard of real-surface flows with screenshots, storage, and exit status. No new work enters here except regression defense.

### Storage, clipboard, and sharing contracts come next

This phase stresses file, preference, clipboard, and share-contract behavior across apps from different authors so layout, persistence, and inter-app data paths harden before media arrives. Entry gate is three to five FOSS-pinnable apps exercising those contracts plus a named owner, and the standing promotion rule applies that a track starts only with a motivating pinned app plus that owner. Proof is all pinned apps at top grade for install, launch, and flow-complete stages across two consecutive runs with previously green utility flows still green, every status carrying logs rather than anecdote.

### Media playback plus camera and sensor-gated apps follow

This phase covers clear-content playback and capture paths using the reimplemented MediaCodec over host codecs with software fallbacks, while MediaDrm reports unsupported outside ClearKey and sensors and location degrade through honest denial rather than crashes. Entry gate is a fresh pinned set of video, social, and camera-exercising apps plus a named owner, with the phase explicitly scoping Widevine-gated HD, banking, and anti-cheat titles out as unrunnable on an uncertified host. Proof is a bounded playback demonstration with pause, seek, loop, hung-decoder timeout, and bounded memory on the motivating app, repeated under default isolation, plus flow-complete grades for the full pinned set across two consecutive runs.

### Networked plus account apps harden identity without Google

This phase exercises sync, offline-to-online transitions, and non-Google auth including password, phone, OAuth, and custom-token paths, deliberately preceding the Play-services phase so account logic proves itself before Google-auth dependence enters. Entry gate is networked pinned apps with distinct backends plus a named owner. Proof is flow-complete grades with account creation, sign-in, token refresh, and offline-degraded behavior, again across two consecutive runs with regression of all earlier phases.

### Play-services-dependent apps reach the microG tier

This phase delivers push registration and delivery, maps display, fused location, and basic auth flows at the level microG marks Full or Mostly, accepting degraded or unavailable behavior for billing enforcement, Play Games sign-in-only logins, Cast, Auto, Wear, fitness, geofencing, Nearby, and in-app updates. Entry gate is pinned apps exercising push, maps, and location from different authors plus a named owner, with real GMS preferred only where licensable and sandboxed-Play-style unprivileged compat otherwise defining the ceiling. Proof is the pinned page or flow rendering and interacting plus clean failure without app crash for the unsupported paths, held across two consecutive runs.

### Native-heavy games close the program on GPU and ABI

This final phase serves GLES 3.2 plus Vulkan 1.1 through ANGLE onto host Vulkan with software fallback, prefers x86_64 native slices where APKs carry them, honors 16 KB page alignment for API-35-targeted artifacts, and reports a coherent feature and GL-version profile so Play filtering and engine feature detection behave. Entry gate is the strongest of all because it requires a named owner plus pinned games spanning Unity, Unreal, and Godot-with-plugins exports, and the ARM-translation question on x86_64 must be answered explicitly before broad ARM integration proceeds, consistent with the standing rule that native proof means one binary executing correctly on hardware before any sprawl. Proof per addition is on its motivating app with no standing scope beyond it, flow-complete grades across two consecutive runs, and the full earlier-phase regression still green.

## Conclusion

The plan reframes compatibility from app count to contract depth, which changes resourcing from parallel app teams to sequential subsystem pushes each unlocked by a single motivating app and owner. The uncomfortable implication is that the final fifteen percent of Play demand in banking, subscription video, and cheat-guarded multiplayer stays permanently red on any uncertified host, so Leadership should judge the program by the runnable set reaching green rather than by store-wide percentages. Holding the vanilla-retest and two-consecutive-green rules matters more than velocity, because those two rules are the only mechanism that keeps per-app accommodations from quietly forking the shared runtime the whole program depends on.
