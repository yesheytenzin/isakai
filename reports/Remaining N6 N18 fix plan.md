# Restore sealed metadata, validate loader, finish navigation

Seven remaining fixes across the N6 translator blockers, the N6 loader-contract follow-ups, the N18 NDK asset proof, the AppCompat icon and navigation gaps, and the notes-save residual flake each reduce to a proven file and a concrete verification, and none of them requires new research before implementation. The sealed-subclass discovery failure is fixed by copying `kotlin.Metadata` annotation bytes in `src/translate.zig`, because `kotlin-reflect` reads the sealed list from that annotation first and only falls back to the JDK sealed path when metadata is absent ([Source](https://raw.githubusercontent.com/JetBrains/kotlin/master/core/reflection.jvm/src/kotlin/reflect/jvm/internal/KClassImpl.kt)). The `AlertDialogLayout` VerifyError is a version-49 inference bug diagnosed with stock `javap` rather than a StackMapTable defect, since classes below version 50 verify by inference and frames do not exist as a failure mode there ([Source](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-4.html)). The loader shim in `src/native/bionic_shim.zig` must validate `android_dlextinfo` flags before any host fallback and attribute `dlerror` per thread, because platform bionic fails unknown flag bits outright and owns the error string in a per-thread 512-byte buffer ([Source](https://raw.githubusercontent.com/LineageOS/android_bionic/lineage-22.1/linker/linker.cpp)). The asset-fd, icon, navigation, density, and notes-save items are contract completions whose proofs run on device or on the app flow, not in documentation. Together they unblock N6 layout inflation and N18 asset-backed playback with narrow, reviewable diffs.

## Sealed discovery returns when the translator preserves kotlin.Metadata verbatim

The `byLowerCase("cube")` null and the empty `getAll()` share one root cause: the translated `BackendName.class` carries **zero class-level attributes** (`src/translate.zig:5138` writes a zero attribute count), so neither `kotlin.Metadata` nor `PermittedSubclasses` nor `InnerClasses` survives translation. That matters because the sealed-subclass list lives inside the `kotlin.Metadata` annotation payload as protobuf field `sealed_subclass_fq_name` ([Source](https://raw.githubusercontent.com/JetBrains/kotlin/master/core/metadata/src/metadata.proto)), and `KClassImpl` resolves `sealedSubclasses` from the parsed annotation first, falling back to JDK `getPermittedSubclasses()` only when the annotation is absent ([Source](https://raw.githubusercontent.com/JetBrains/kotlin/master/core/reflection.jvm/src/kotlin/reflect/jvm/internal/KClassImpl.kt)). With metadata dropped, `kmClass` is null and the Kotlin path is dead; the JDK fallback is dead too because no `PermittedSubclasses` attribute is emitted, so the call returns `emptyList()` silently rather than throwing, which is exactly the observed symptom. A `when` over the hierarchy keeps working through plain `instanceof` chains, which is why only the reflective path breaks.

The **proven-correct fix lives in `src/translate.zig`**: emit `RuntimeVisibleAnnotations` on translated classes and copy every runtime-visibility DEX annotation byte-for-byte, which restores the primary `getSealedSubclasses()` path with **no Kotlin knowledge and no protobuf decoding**, since the lenient metadata reader tolerates version skew between the app's Kotlin version and the runtime's ([Source](https://github.com/jetbrains/kotlin/blob/master/libraries/kotlinx-metadata/jvm/ReadMe.md)). The one subtle step is name rewriting: subclass entries resolve through `classLoader::loadKClass`, and the translator relocates nested `BackendName$CUBE` classes to top-level names, so stale fully-qualified names in the copied `d1`/`d2` payload are skipped silently by `mapNotNull` and reproduce the identical empty-list symptom. Optionally, synthesizing `PermittedSubclasses` plus `InnerClasses` restores the JDK-native path (`isSealed()` true, `getPermittedSubclasses()` non-null per the Java 17 contract ([Source](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Class.html))), but kotlinc only emits that attribute for JVM 17 targets ([Source](https://github.com/jetbrains/kotlin/blob/master/compiler/ir/backend.jvm/codegen/src/org/jetbrains/kotlin/backend/jvm/codegen/ClassCodegen.kt)), and whether HotSpot honors it on a major-v49 class file is untested, so the annotation copy is the version-independent fix and the attribute synthesis is the optional hardening. Before editing, run the diagnostic ladder that distinguishes a translator bug from a build-config bug: `javap -v` on the translated class should show all three pieces absent, jshell should show `isSealed()` false with `getPermittedSubclasses()` null, and `dexdump` of the source DEX should be checked for `Lkotlin/Metadata;`, because if R8 stripped the annotation upstream the fix is a keep-rule, not translator work. Verification is `javap -v` showing `kotlin.Metadata` present with relocated subclass names, jshell `getAnnotation(Metadata.class)` non-null, and the app probes `byLowerCase("cube")` non-null with `getAll()` returning the full subclass set.

## AlertDialogLayout VerifyError is a v49 inference bug found with javap alone

The translator pins its output to **major version 49** (`src/translate.zig:5077`), which moves the entire VerifyError analysis off the familiar StackMapTable ground: classes below version 50 verify by type inference, type checking with frames is mandatory only at 50 and above, and the inference fallback for failed type checking exists solely at exactly version 50 ([Source](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-4.html)). For `AlertDialogLayout.onMeasure`, StackMapTable defects and generic `Signature` confusion are therefore ruled out structurally, and the suspect list narrows to **uninitialized-object misuse around `new`+`<init>` pairing, `long`/`double` two-slot discipline, branch-merge type mismatches across the many early-return and panel-null joins in `tryOnMeasure`, and wrong method or field descriptors** such as int-vs-float opcode selection or a narrowed receiver tripping protected access ([Source](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-4.html)). Local history reinforces the descriptor-first prior: the translator previously emitted `iaload` for a `float[]`, used forward-constructor `iload` for float and double parameters, and narrowed receivers to `java/lang/Object` until protected-access verification forced the never-narrow rule. The `storeTracked` invariant in `src/translate.zig`, where stores deliberately do not clear pending new-instance types, is the first place to re-examine if the eventual message mentions `<init>` or uninitialized values.

The **fix has no predetermined file until the message is read**, and the workflow needs only stock JDK tooling on the Temurin 27 already used in-session: capture the full `VerifyError` text with its method and `bci=@N` offset, locate offset N with `javap -c`, confirm the v49 absence of frames with `javap -v`, then cross-check the call descriptors at N against the AndroidX source, where `onMeasure` delegates to `tryOnMeasure` with its three-panel top, content, and button measurement contract ([Source](https://raw.githubusercontent.com/androidx/androidx/androidx-main/appcompat/appcompat/src/main/java/androidx/appcompat/widget/AlertDialogLayout.java)). Verification is two-layered because class-load success alone proves nothing about layout: the `VerifyError` must be gone **and** the translated method must reproduce the documented panel distribution of wrap-content top panel, fill-priority content, and min-height button panel. The actual failing message and disassembly were never captured in repo history, so the ranked suspects above are a prior and the first action is capturing the message, not editing the emitter.

## Single-namespace loader must validate extinfo first and attribute dlerror per thread

The `android_dlextinfo` struct carries **seven fields gated by a `flags` bitmask** with platform-defined validity rules ([Source](https://developer.android.com/ndk/reference/structandroid/dlextinfo)), and the current shim in `src/native/bionic_shim.zig:191` ignores `extinfo` entirely while forwarding to `dlopen`. Platform bionic rejects unknown flag bits, rejects `USE_LIBRARY_FD_OFFSET` without `USE_LIBRARY_FD`, and rejects `USE_NAMESPACE` with a null namespace, each by failing the load ([Source](https://raw.githubusercontent.com/LineageOS/android_bionic/lineage-22.1/linker/linker.cpp)), while NULL `extinfo` is the legal plain-`dlopen` path in the caller's namespace ([Source](https://raw.githubusercontent.com/LineageOS/android_bionic/lineage-22.1/linker/dlfcn.cpp)). The **proven-correct fix in `src/native/bionic_shim.zig`** validates before any host attempt: NULL `extinfo` forwards as today, unknown bits and bad combinations fail, the WebView-only RELRO and reserved-address bits fail loudly rather than being silently ignored, and `USE_NAMESPACE` fails loudly because the shim has exactly one namespace and cannot emulate isolation. Validation must precede the host-first fallback because a `USE_NAMESPACE` request the host would happily satisfy must still fail, otherwise host success silently violates the caller's contract. The `dlopen` flags themselves need the same treatment since bionic rejects anything outside its six accepted bits ([Source](https://raw.githubusercontent.com/LineageOS/android_bionic/lineage-22.1/linker/linker.cpp)).

The `dlerror` half of the fix is about ownership, not text. The error string lives in a **per-thread 512-byte buffer the caller must never free**, every failing `dlopen`, `dlsym`, or `dlclose` overwrites it, success leaves it untouched so stale errors survive later successes, and `dlerror()` atomically returns the pending pointer and clears it so a second consecutive call yields NULL ([Source](https://raw.githubusercontent.com/LineageOS/android_bionic/lineage-22.1/linker/dlfcn.cpp)). Concretely, guest `dlsym` failure on a tracked handle must write the shim's thread-local buffer, guest success must not clear a pending host error, and a failed host attempt followed by a successful bionic load must clear while a failed bionic retry must surface the bionic message rather than the stale host one. The shim's `threadlocal err_buf` already mirrors the 512-byte size, and its `trackHandle`/`isTracked`/`untrackHandle` routing of `dlsym` and `dlclose` by handle identity matches the platform rule that handle lookups route by identity and never retry another loader ([Source](https://raw.githubusercontent.com/LineageOS/android_bionic/lineage-22.1/linker/linker.cpp)). Host-first ordering itself stays because HotSpot and glibc-built JNI libraries require exact glibc semantics and only libraries glibc rejects can be Android DSOs, but it must be documented as an isakai-only rule since platform bionic has no host-guest split at all. Verification is a targeted test matrix: bad-flag-bits and OFFSET-without-FD loads fail, `USE_NAMESPACE` fails loudly, NULL `extinfo` loads as before, consecutive `dlerror()` calls return message-then-NULL, and a guest failure after a host error surfaces the guest text. Two gaps stay open by design: guest `RTLD_DEFAULT`/`RTLD_NEXT` semantics across the two-loader boundary need an N6 decision rather than more research, and whether any pinned app library passes non-NULL `extinfo` needs a grep over the app libs that was never run.

## NDK asset fd proof needs a stored entry, a compressed entry, and a caller grep

`AAsset_openFileDescriptor` returns a real file descriptor plus offset and length **only for uncompressed `Stored` entries**; for `Deflated` entries the implementation is a one-line unconditional `-1`, and the NDK contract states plainly that a negative return means direct fd access is not possible, for example when the asset is compressed ([Source](https://developer.android.com/ndk/reference/group/asset)). The bridge shape in tree already honors this: `isakai_asset_fd` in `src/native/res_engine.cpp` forwards to `openFileDescriptor` and propagates `-1`, the Zig bridge in `src/bridge/resources.zig` null-checks and forwards with 32-bit truncation documented, and the open-then-close probe in `isakai_asset_range` returns before `close` only on the `fd < 0` path so no descriptor leaks. **No bridge change is needed for the compression rule itself**; the remaining N18 work is a device proof plus the caller hunt. The proof drives two concrete assets from the pinned APK: a known-uncompressed entry must yield `fd >= 0` with `pread` at the returned offset and length reading intact bytes, and a known-compressed entry must yield `fd < 0` with the caller falling back to stream reads rather than treating it as fatal. The caller hunt is the grep that was never run: enumerate every NDK call site reaching `openFd` in the pinned app libraries to confirm which assets the app actually memory-maps versus streams, since Stored-versus-Deflated is an `aapt` packaging decision and not a runtime one. Verification is the two-asset device run plus the completed caller list, with the dispatch detail of which `ZipFileRO` compression check selects the asset subclass explicitly left uncited because the class-level behavior already determines the contract.

## Icon, Up navigation, density, and the notes flake close with small framework reads

The FAB-plus-icon gap is a missing attribute read, not a missing drawable pipeline. The repo's `ImageView` constructor reads only `android:src` as a raw id and ignores `app:srcCompat` entirely, while the platform pattern resolves `android:src` as a `Drawable` off the `TypedArray` ([Source](https://developer.android.com/reference/android/content/res/TypedArray)) and `srcCompat` as a resource id with a `-1` default meaning unset ([Source](https://developer.android.com/reference/android/content/res/TypedArray)), applying the srcCompat drawable last so it wins when both are present. The **fix in `framework/android/widget/ImageView.java`** adds the `getResourceId(..., -1)` read, skips when `-1`, loads through the `AppCompatResources`-equivalent path with `NotFoundException` propagating for unknown ids per the platform contract that zero is invalid and missing ids throw ([Source](https://developer.android.com/reference/android/content/Context)), and applies srcCompat after `android:src`. Verification is the picker screenshot showing the intended container blue with a visible plus instead of the black blob, paired with a calculator repaint proving no color shift, since the canvas filter consumption in `framework/android/graphics/Canvas.java` is the companion half already analyzed. The exact AndroidX styleable indices and tint ordering were never retrieved against citable source, so the `-1` guard and application order above are the contract-minimum implementation and tint-attribute handling waits on an AndroidX source read.

Up navigation and density are the same kind of contract completion with exact deltas. `navigateUpTo` takes **exactly one up intent**: when the destination already sits in the task history every intervening activity finishes and the intent is delivered, otherwise the task finishes down to the root in in-app-home behavior, returning true only when the destination was reached ([Source](https://developer.android.com/reference/android/app/Activity)). The repo's `Activity.navigateUpTo` instead launches the intent and finishes only self on the not-found path while never delivering on the found path, and `getParentActivityIntent()` returns null unconditionally instead of resolving `parentActivityName` from the manifest ([Source](https://developer.android.com/reference/android/app/Activity)). The **fix in `framework/android/app/Activity.java`** adds intent delivery on the found path, finish-to-root with a false return on the not-found path, manifest parent resolution, and the `shouldUpRecreateTask` branch that synthesizes the parent stack through `TaskStackBuilder` for cross-task Up ([Source](https://developer.android.com/reference/android/app/TaskStackBuilder)). Density must be supplied as **one mutually consistent snapshot**: `getDrawableForDensity` with density zero falls back to the configuration density ([Source](https://developer.android.com/reference/android/content/res/Resources)), so the `Resources` instance behind drawable selection and the metrics behind dp-to-px layout must share the compositor snapshot, which the repo's `setMetrics` plus `applyMetrics` shape already does. Verification is a scrolled-container probe asserting reported position, drawn position, and touch target agree, plus a cross-density run showing correctly chosen drawables at correct pixel sizes. The precise found-path delivery mechanism wants one AOSP source check before reimplementation.

The notes-save residual flake is the last item and its next step is a trigger fix, not a watcher fix. The earlier gate reversal moved fresh-tree saves from **zero of six to five of six**, with the single miss an empty editor where paste never landed and the skip was correct. The remaining intermittency is structural: opening a picker dialog over the editor fires **no lifecycle or page-change callback at all**, so any save hung on `onPause`, `onStop`, or page selection is bypassed exactly on the picker path, while `onPause` remains the only guaranteed persist point when the UI leaves the foreground ([Source](https://developer.android.com/guide/components/activities/activity-lifecycle#onpause)). The **fix is an explicit synchronous flush of `getText()` into the model and UPDATE before `dialog.show()`**, plus the unconditional `getText()` re-read at the trigger so a stale watcher-fed field can never lose data, keeping the `onPause` and page-change saves as backstops for non-dialog exits. Verification reuses the pinned `sway-flow.py notes` series asserting a database UPDATE on both the picker-open-then-confirm flow and the swipe-away flow, with the write call-site thread asserted on a background executor independently of the trigger firing.

## Conclusion

The pattern across all seven items is that the contract was already written down and the code is one narrow edit behind it: the annotation copy, the extinfo validation, the error-buffer attribution, the srcCompat read, the single-intent Up rule, and the pre-dialog flush each mirror a platform statement with a file attached. The highest-leverage ordering runs the sealed-metadata copy first because every reflective Kotlin path stays dark without it, then the VerifyError capture because layout inflation gates everything behind it, then the loader validation because silent contract violations compound, with the device proofs and framework completions trailing in any order. What changes going forward is diagnostic discipline: the jshell and `javap` probes that distinguish translator bugs from build-config stripping, and the two-flow save verification that separates trigger failures from write failures, turn each future recurrence from an investigation into a checklist.
