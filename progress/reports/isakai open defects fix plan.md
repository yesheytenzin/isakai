# Fix scrolled pages, tint filters, and erase

The six open defects collapse to three framework repairs, one runtime repair, and two contract completions, each with a proven file and a concrete screenshot-or-database proof. The notes body-save intermittency is a scrolled-pager disagreement where display, touch, and the logical page point at different fragments, fixed once in `ViewGroup.java` with a 0/6-to-5/5 save gate reversal. The black FAB blob is a dropped `Paint` color filter at the software canvas, fixed in `Canvas.java` on top of already-landed state delivery. The picker whitewash needs a narrower erase-preserving change in `View.java` because the reverted global transparency provably garbles repeated-pass screens. The two Compose cosmetics cannot be fixed framework-side at all and need small record-and-invalidate repairs inside the translated runtime the app ships. File-picker cancel and `getLocationInWindow` are contract completions with exact verification steps. Three items stay explicitly out of scope by policy and staffing, recorded at the end.

## Scrolled pager starves the body save while the title lands

The notes failure has the sharpest before-and-after proof in the whole set. On the clean tree six fresh runs all fail with the same signature, dialog confirm writes the title row and the body `UPDATE` never compiles, with database rows stuck at `(1,'General note',''), (2,'N2','')`. SQL probing across those runs plus five instrumented runs finds only seed and confirm `INSERT`s and zero `UPDATE`-family statements on any `execSQL` or `execute` path. Field inspection on a failing run explains why the write is correctly skipped: the pager adapter map holds `{0=General-frag, 1=N2-frag}`, the save routine `g8/g.W` runs on the N2 fragment whose editor field `q0` is an empty unfocused `MyEditText`, while the typed marker sits in a different focused editor belonging to the position-0 fragment, so `U()` returns empty and the equals-skip fires with no exception anywhere. Watchers fire on every edit path, focus is correct, Room works, and touch mapping is one-to-one on a headless session, which isolates the defect to which fragment the user sees and touches versus which fragment the save reads.

The pager provably sets `scrollX=640` with `currentItem=1`, but the framework never applies scroll in touch dispatch or child drawing, so display stays on page 0 and taps hit page 0 while the save reads page 1. The **proven-correct fix lives in `framework/android/view/ViewGroup.java` only**, adding `getScrollX()` and `getScrollY()` at the four touch-dispatch offset sites and painting children at `(offsetX - getScrollX(), offsetY - getScrollY())` in `dispatchDrawAt`, mirroring the platform contract where touch hand-off uses `offsetX = mScrollX - child.mLeft` and scrolled content paints shifted by the scroll amount. This file is **high-blast-radius** because every view group dispatches through it, but the change is inert at zero scroll and a probe census shows only the notes `MyViewPager` ever sets nonzero scroll, with calculator, OpenCalc, and dialog flows never scrolling. Verification is the pinned `sway-flow.py notes` series on fresh trees, asserting the database row carries the marker after picker-open, then restart, reopen-edit, liveness, and clean close, which moved from **0/6 saves before to 5/6 full passes after** with the single failure an empty editor where paste never landed and the gate correctly skipped, plus calculator `2+2=4` and OpenCalc `12+34=46` regression passes on the same build. The deferred companion is `getLocationInWindow` scroll adjustment, explicitly untouched because nothing in the save path uses it.

## Blue tint dies at the canvas after state delivery started working

The FAB blob is opaque black in a 56x56 round rect drawn through `RippleDrawable` into the Material shape path, while the intended container blue `FF7A90C8` is present in the background tint list and never reaches the fill. Temporary diagnostics proved the state-delivery machinery engages, with the floating-action-button background reporting stateful ripple and static row backgrounds correctly untouched, yet the pixels stay black. Bytecode analysis one layer down found why: the blue arrives via `setTintList` into a computed `PorterDuffColorFilter` stored on the paint through `paint.setColorFilter`, and the software canvas never reads it, since `Canvas.paintColor` folds only color and paint alpha with no filter consumption on any draw path. The platform contract is explicit that when a drawable has a color filter each output pixel is modified by the filter before blending ([Source](https://developer.android.com/reference/android/graphics/drawable/Drawable)), that drawable drawing respects color filter alongside alpha ([Source](https://developer.android.com/reference/android/graphics/drawable/AnimatedImageDrawable)), and that the default tint mode is `SRC_IN` ([Source](https://developer.android.com/reference/android/graphics/drawable/Drawable)), with the role assignment that the filter color is source and the drawn content is destination so opaque shapes take the tint color exactly.

The **proven-correct fix lives in `framework/android/graphics/Canvas.java`**, applying `paint.getColorFilter()` inside `paintColor(Paint)` so every paint-driven op filters then blends, plus per-texel filtering in the `Paint`-taking `drawBitmap` overloads, while paint-less `drawColor(int)` stays unfiltered. The already-landed state work in `framework/android/view/View.java` (`drawableStateChanged` pushing `getDrawableState()` into stateful backgrounds with `refreshDrawableState` wired from pressed, enabled, selected, background, and attach) plus the `InsetDrawable` state-forwarding companion and the `ImageView` `android:src` inflation read are prerequisites to keep, since pressed and disabled shades flow through them once the canvas honors the filter. `View.java` is **high-blast-radius** and `Canvas.java` touches every draw, so verification must pair the target with isolation: drive the notes picker and screenshot the button blue with a visible plus against the pre-change black blob, then repaint the calculator settings and keypad pre-to-post to prove no double-draw or color shift, since the earlier global-transparency attempt proved a pixel-neutral claim needs that isolation pair. The `SRC_IN` integer math with round-to-nearest alpha multiplication is already correct in tree and needs no change beyond the consumption point ([Source](https://developer.android.com/sdk/api_diff/29-incr/changes/android.graphics.PorterDuffColorFilter)).

## Whitewash needs opaque erase first and styling second

Picker rows are app-intended periwinkle `FFEEF0FF` set at runtime as a single-layer `LayerDrawable` over a programmatic gradient, confirmed by tree dumps showing correct stacking and by probes showing the raw field already periwinkle with null tint. The defect is the framework painting opaque white over every background-less view, because `View.backgroundColor` defaults to white and `View.onDraw` fills it, so each title and body text view covers its own row background and only the strip beside short titles survives as bars. The first repair attempt defaulted the background to transparent and guarded the fill, which did restore full periwinkle rows but garbled the calculator settings screen into two-to-three-times superimposed text, with pre-change, mid-state, and items-2-and-3-only isolation runs proving the transparency is the cause. The old comment calling the fill intra-frame erase between repeated passes was load-bearing: transparent writes are a documented no-op in this rasterizer because alpha zero leaves the destination pixel untouched, and re-drawn antialiased text provably darkens without an opaque reset through the glyph pre-blend path, while only `SRC` or `CLEAR` mode replaces through the raw path. The platform analog is that opaque views guarantee full-bounds opaque coverage and the hierarchy may optimize around that promise ([Source](https://developer.android.com/reference/android/view/View)), that `drawColor` fills are clip-scoped source-over overdraw ([Source](https://developer.android.com/reference/android/graphics/Canvas)), and that the software surface must rewrite every pixel unless a dirty rect preserves the rest ([Source](https://developer.android.com/reference/android/view/SurfaceHolder)).

The **correct fix lives in `framework/android/view/View.java` (high-blast-radius)** and must be narrower than the reverted attempt: restore the opaque frame clear in `Activity.paintRoot` as the once-per-presented-frame base, then shrink per-view fills from unconditional erase to actual background styling or `isOpaque()`-driven hints, verifying text-heavy screens and animation frames for accumulation. Verification is a repeated-pass screenshot comparison over one buffer on the settings-toggle and animation flows, comparing glyph edge darkness with and without the opaque frame clear, plus the picker acceptance of full-width periwinkle rows with text on top and no white bars. The reverted global default must not be re-applied as-is.

## Black arrow and clipped row are compose-issued and need runtime hooks

The two Compose cosmetics look like framework bugs and probe as runtime bugs. Compose renders in strictly ordered composition, layout, and drawing phases with unidirectional data flow ([Source](https://developer.android.com/develop/ui/compose/phases)), where each composable maps to a layout node and icons draw as single-color 24dp glyphs tinted through the same tint mechanism as images ([Source](https://developer.android.com/develop/ui/compose/graphics/images/material)). Tinting uses `ColorFilter.tint` with `SrcIn` by default ([Source](https://developer.android.com/develop/ui/compose/graphics/images/customize)), layers isolate instructions similar to `RenderNode` for efficient re-issue ([Source](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers)), and without an offscreen buffer `Clear` leaves the black window buffer visible where layer content is absent ([Source](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers)). Magenta-swap isolation proves the back-arrow vector renders perfectly with twelve verbs but sits under a compose-issued opaque-black 24x24 `drawRect` at the nav slot origin drawn immediately before the path, while the first-row clip probes show settled text at the correct position below the app bar covered by identical same-frame draws at stale offsets with white row rects on top. The `RenderNode` and `Picture` replay paths are dead code with no callers, and the translated `AndroidComposeView` and `ViewLayer` are app-shipped with only stubbed framework APIs touched, so the duplicates are re-issued recorded instructions with a stale transform, the predictable failure when a placement read lands in the wrong phase and the isolated layer replays without re-recording.

No host interception can correct either artifact without reimplementing composition, because the host sees only undifferentiated canvas commands from one view and cannot tell a stale rect from a legitimate one, while deduplication would corrupt legal overlapping tints and shadows and forced full re-record would destroy the phase-skipping performance model without restoring missing glyph commands. The **minimal repair lives in the translated compose runtime the app ships (obfuscated `r1.*`, not `framework/`)**: for the black box implement or un-stub the exact blend path the icon painter uses, plausibly paint transfer-mode or `SrcIn` tint over the vector, with fallback to drawing the vector un-tinted so a cosmetic tint error replaces a black box; for the duplicates ensure placement changes invalidate or reposition the isolated layer so a move re-issues only at the new offset. Verification needs a dedicated draw-instrumentation session tracing which translated call emits the bounds fill and which placement step skips invalidation, with before-and-after screenshots of the arrow slot and first-row glyph tops plus liveness through the existing calculator flow. The adjoining header truncation from `GENERAL` to `GENER` is already fixed by advance-based line breaking in `Layout.java` and rounded fills by device-space `drawRoundRect` in `Canvas.java`, while the unchecked outline at one-pixel radius is correct per the Material checkbox spec and needs no change.

## Cancel propagation and scrolled coordinates complete the contracts

File-picker cancel has a fully specified chain and a thin remaining proof gap. A cancel must travel picker dismissal into the result dispatcher as `onActivityResult` with the original request code intact, where deny and error map to `RESULT_CANCELED` and production delivery is callback-based rather than blocking. The in-tree hand-offs preserve the code through `pendingFileRequestCode`, per-frame `pollDesktopResults` draining the desktop queue with kind-12 status `-1` delivering `RESULT_CANCELED`, and the activity-stack parent forwarding untouched, while the `startActivity` delegation path correctly owes no result for its negative code. The bridge poll operation now measures **0.0 to 0.1 milliseconds** with the old up-to-one-second blocking settle removed, and the window loop drains every slice at roughly one-tenth of a second, so a queued cancel-shaped event is app-visible within about one slice plus app handling. The **owning files are `src/dbus_bridge.zig` for the nonblocking drain already shipped and `framework/android/app/Activity.java` for the every-slice drain and kind-12 delivery**, with no further edit planned. Verification still owed is end-to-end through a real portal picker asserting `RESULT_CANCELED` with the original code, since the headless fixture has no file portal and `open-file` stays pending by design, and no pinned flow issues a content or document intent today.

Scrolled coordinates are the mirror image, where touch and draw already agree and reporting lags. The in-tree touch path adds back group scroll and the draw path paints children shifted by the scroll, so hit-testing matches what is displayed whenever scroll values are real. The gap is that `getLocationInWindow` walks parents summing left and top with no ancestor-scroll subtraction and `getLocationOnScreen` aliases it with no window-to-screen offset, which over-reports scrolled content position. The platform distinguishes window coordinates from screen coordinates and warns they differ under letterboxing ([Source](https://developer.android.com/develop/ui/views/layout/display-cutout)), with left and top defined relative to parents ([Source](https://developer.android.com/develop/ui/views/layout/declaring-layout)). The **fix lives in `framework/android/view/View.java` (high-blast-radius)**, subtracting each ancestor scroll during the window walk and adding the window-to-screen offset for the screen variant, checked verbatim against the platform `View.java` before finalizing the math. Verification is a scrolled-container probe asserting reported position, drawn position, and touch target agree, reusing the notes pager census as the live scrolled case.

## Conclusion

The plan deliberately leaves three items unaddressed because evidence rules and staffing require it, and treating them as open engineering tasks would mislead the next reader. Keymap reorder and delay stress stays excluded by the verification-artifact policy since no existing tool can inject adversarial keymap sequences and building one is forbidden without an exception. The privileged confinement operator run and the independent non-self review both need a human with authority and fresh eyes, so they are recorded as staffing gates rather than planned diffs. What remains is a short sequenced execution: land the canvas filter, then the erase-preserving view change with its isolation repaints, then the window-reporting scroll math, while the translated-runtime arrow and duplicate work proceeds in its own instrumented session and the picker-cancel flow waits for a portal-capable fixture.
