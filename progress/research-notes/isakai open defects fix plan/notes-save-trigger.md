# Note-editor save-trigger contract (ViewPager editor; INSERT works, body UPDATE on picker-open intermittent)

## Do TextWatcher callbacks fire on every text mutation — IME commitText, paste, programmatic setText — and what breaks if they do not?

### Takeaway
Official contract: every mutation of the text — `setText`, key input, IME `commitText`/`setComposingText`, paste, delete — is delivered to registered `TextWatcher`s as a `beforeTextChanged` / `onTextChanged` / `afterTextChanged` triple with precise change spans; a watcher-updated model therefore always matches the buffer. This repo's framework fires watchers only from `TextView.setText`, with full-replace spans on every call and no `Editable`-level dispatch — so watcher code that depends on the `(start, before, count)` spans, or on `afterTextChanged` mutating a shared buffer, silently misbehaves even though "a callback happened".

### Cited Findings
- `TextWatcher` defines exactly three callbacks — `beforeTextChanged(CharSequence s, int start, int count, int after)`, `onTextChanged(CharSequence s, int start, int before, int count)`, `afterTextChanged(Editable s)` — and the documented contract is that they are called when the text is changed, with `start/before/count` locating the precise changed region ([Source](https://developer.android.com/reference/android/text/TextWatcher)).
- In AOSP, IME text arrives through `InputConnection.commitText` / `setComposingText`, which mutate the `Editable` buffer; the buffer is a `SpannableStringBuilder` that dispatches to its registered span watchers, and `TextView` registers itself so every IME/paste/key mutation fans out to `TextWatcher`s with exact spans ([Source](https://developer.android.com/reference/android/view/inputmethod/InputConnection#commitText(java.lang.CharSequence,%20int)); [Source](https://developer.android.com/reference/android/text/SpannableStringBuilder)).
- Programmatic `TextView.setText` also fires the full watcher triple in AOSP (it goes through `setText(CharSequence, BufferType)` → buffer replace → span dispatch), so watchers cannot distinguish "user typed" from "code set" except via a self-change guard flag ([Source](https://developer.android.com/reference/android/widget/TextView#setText(java.lang.CharSequence))).
- Paste from the clipboard is delivered as a text-replace operation on the same buffer (context-menu paste and `Ctrl+V` both resolve to a replace of the selected range), i.e. it fires watchers exactly like typing ([Source](https://developer.android.com/reference/androidx/core/view/ContentInfoCompat)).
- In-repo (read-only assessment): `framework/android/widget/TextView.java` keeps its own `watchers` list and fires the triple **only** inside `setText` (`TextView.java`, `setText(CharSequence)`), always with degenerate full-replace spans `beforeTextChanged(old, 0, old.length(), next.length())` / `onTextChanged(next, 0, old.length(), next.length())`. `SpannableStringBuilder` in this repo has **no** watcher/span dispatch at all (grep for Watcher/dispatch in `framework/android/text/SpannableStringBuilder.java` returns nothing), and `Editable` is a bare mutation interface (`framework/android/text/Editable.java`).
- In-repo funneling (all roads lead to `super.setText` → watchers fire, but coarsely): `EditText.replaceSelection` (typing, DEL, `Ctrl+V` paste via `paste()`, ENTER newline) → `refresh()` → `super.setText(...)` (`EditText.java`, `replaceSelection`/`refresh`); key-listener path → `notifyEditableChanged()` → `refresh()`; `BaseInputConnection.replace` (`commitText`/`setComposingText`) and `deleteSurroundingText` → `changed()` → `notifyEditableChanged()` → `refresh()` (`BaseInputConnection.java`, `changed()`).
- In-repo gap paths that fire **nothing**: any direct mutation of the live buffer via `getText().insert/delete/replace/...` by app code bypasses watchers entirely (no `Editable`-level dispatch exists), and leaves the `TextView.text` field stale until the next `refresh()`/`setText` (note `EditText` overrides `getText()` to return the live `Editable`, while `TextView.length()`/`append()`/`selectAll()` operate on the two stores inconsistently).
- In-repo `afterTextChanged` fidelity: for `EditText` the live buffer is passed (since `getText()` returns the `Editable`); for plain `TextView` a throwaway `editableFactory.newEditable(next)` copy is passed, so watcher edits to it are lost (`TextView.java`, `setText` tail).

### Inferences
- If the note editor keeps its "current body" in a field updated from `afterTextChanged`/`onTextChanged`, then in this repo the model **does** update on typing/paste/IME (via the `refresh()` funnel) — but any logic using the span args (e.g. incremental diffing, "only save if changed region X") sees a whole-text replace every keystroke and may mis-fire or no-op.
- The intermittent "body UPDATE never runs" is unlikely to be "watchers never fire on typing" in this repo; more likely suspects are (a) app code mutating `getText()` directly with no watcher delivery, or (b) the save trigger itself (lifecycle/dialog path, Q4) never running — the UPDATE statement is only as reliable as the trigger that issues it.
- Any fix that relies on precise spans must either fix `TextView.setText` to compute real diff spans or, more cheaply, make save logic span-insensitive (compare full strings / always mark dirty on any callback).

### Gaps
- Context7 full-text search returned no verbatim TextWatcher reference prose; the span-precision claim above rests on the canonical reference page and long-standing AOSP behavior, not on a retrieved snippet. No in-repo AOSP `setText(CharSequence, BufferType)` / `mListeners` span machinery exists to compare against, so "what AOSP would do here" is contract knowledge, not locally verified.
- I did not verify which exact watcher consumer the notes app (SimpleMobileTools Notes, shipped as a compiled APK under `.cache/isakai/apks/`) registers — only `.class` files are present, no decompiled source was read.

## What is the standard pattern for persisting editor content: TextWatcher-updated model, direct getText read at save time, debounced autosave, onPause save?

### Takeaway
Official guidance is unambiguous on one point: persist user data in `onPause` (it is the only lifecycle callback guaranteed to run when the UI leaves the foreground), and treat everything else — `TextWatcher`-updated models, `getText()` reads, debounced autosave — as convention layered on top. The robust combination is a watcher-maintained dirty flag/model plus an unconditional `getText()` re-read at the `onPause` (or equivalent deterministic) save point, so a missed callback can never lose data.

### Cited Findings
- "If the system destroys or stops your activity… you should save… in `onPause()`" — the Activity lifecycle guide positions `onPause` as the persist point because it is the last callback guaranteed before the activity becomes killable; `onSaveInstanceState` is explicitly **not** for persistence (bundle-size limits, only called when the activity is being stopped with state to restore, not a data store) ([Source](https://developer.android.com/guide/components/activities/activity-lifecycle#onpause)).
- `ViewModel` + `SavedStateHandle` only survives process death for small UI state written before stop, and "state updates might be lost if the app process is killed before becoming foregrounded again… SavedStateHandle is saved when onSaveInstanceState is called" — i.e. not a substitute for database persistence ([Source](https://developer.android.com/topic/libraries/architecture/views/viewmodel/viewmodel-savedstate-views)).
- Common-app convention (not contract): update the in-memory model on every `afterTextChanged`, and either (a) debounce (~300–500 ms) a background write for crash safety, or (b) write unconditionally at a deterministic trigger (`onPause`, page swipe, explicit save button). Debounce is a data-loss-reduction convention; `onPause` is the correctness backstop.
- Reading `getText()` directly at save time instead of trusting a watcher-fed field is strictly more robust: it is immune to missed/coalesced callbacks, span bugs (cf. this repo's full-replace spans), and direct-buffer mutations that bypass watchers.

### Inferences
- For this defect ("dialog-confirm INSERT works; body UPDATE on picker-open intermittently never runs"): the INSERT path has an explicit user-confirmed trigger, while the UPDATE path apparently depends on a trigger that does not reliably fire. The fix direction is to (1) re-read `getText()` at the trigger instead of trusting a cached model, and (2) move/add the trigger to a callback that provably fires on the picker-open path (see Q4) — ideally both, so neither a stale model nor a missed trigger alone loses data.
- A debounced autosave would mask but not fix a broken trigger; given the symptom is "UPDATE never runs", the trigger (not the write path) is the first place to look.

### Gaps
- No official "note-editor autosave" pattern page exists; debounce intervals and watcher-vs-read choices are community convention, and I found no citable authoritative interval. Stating a specific millisecond value as "standard" would be fabrication.
- I did not trace the notes app's actual save call sites (compiled APK only); the INSERT-vs-UPDATE trigger asymmetry is taken from the task statement.

## Room write threading norms: which executor, main-thread queries allowed or not, what happens on conflict/timeout?

### Takeaway
Room hard-fails database access on the main thread by default (`IllegalStateException` unless `allowMainThreadQueries()` is set, which exists for testing only); production writes belong on a background executor — a single-threaded/serial executor or Kotlin coroutines on `Dispatchers.IO` — via `suspend` DAO functions, RxJava/`ListenableFuture` return types, or an explicit executor. Conflict handling is per-statement via `@Insert(onConflict = …)` strategy, not via timeouts.

### Cited Findings
- "Room ensures that Database is never accessed on the main thread because it may lock the main thread and trigger an ANR… you should always use async alternatives or manually move the call to a background thread. You may want to turn this check off for testing" via `allowMainThreadQueries()` ([Source](https://developer.android.com/reference/androidx/room3/RoomDatabase.Builder)).
- Room DAO writes are expected to be `suspend` functions (coroutines), RxJava types, or `ListenableFuture`/`Guava` async returns; Room moves `suspend` queries off the main thread itself, and Room's own query executor defaults to a shared background pool — app code must never block the main thread waiting on the result ([Source](https://developer.android.com/training/data-storage/room/accessing-data)).
- There is no Room-level write "timeout" that silently drops an UPDATE: a conflicting concurrent write either follows the declared `@Insert(onConflict = OnConflictStrategy.…)` policy (`REPLACE`/`IGNORE`/`ABORT`) or throws `SQLiteConstraintException`; an unobserved exception in a fire-and-forget background write looks exactly like "the UPDATE never ran" ([Source](https://developer.android.com/reference/androidx/room/Insert)).
- `allowMainThreadQueries` "disables the main thread query check… generally discouraged for production but can be useful for testing" — a main-thread write that "works" in a debug/test build and ANRs or is stripped in production is a known failure mode ([Source](https://developer.android.com/reference/androidx/room3/RoomDatabase.Builder)).

### Inferences
- "Body UPDATE intermittently never runs" is consistent with a fire-and-forget background write whose exception is swallowed (constraint conflict, closed DB, executor shutdown) — writes should be logged/observed, and the executor should be a single serial executor (or `Dispatchers.IO` + `suspend` DAO) so rapid INSERT-then-UPDATE sequences cannot reorder.
- If the app under test enables `allowMainThreadQueries` (common in small note apps), threading is likely *not* the culprit and attention should stay on the trigger (Q4); if it uses a custom executor, verify the executor is alive at picker-open time and that errors propagate to logcat.
- Main-thread vs background must be separated in any fix verification: assert the write call site's thread (background executor, never main) independently from asserting the trigger fires.

### Gaps
- I did not inspect the notes app's actual `NotesDatabase` / DAO threading (compiled `.class` files only under `.cache/isakai/baseline/`); which executor it uses and whether `allowMainThreadQueries` is set are unverified.
- Room's internal `queryExecutor`/`transactionExecutor` defaults (`ArchTaskExecutor` serial + fixed pool) were not re-verified via retrieval; executor-shape claims above are standard documented behavior but cite the access-data guide generally.

## FragmentStatePagerAdapter/ViewPager page-change vs dialog-open: which lifecycle callbacks reliably fire when a picker dialog opens over an editor?

### Takeaway
Opening a `DialogFragment`/picker dialog over an editor does **not** pause or stop the underlying activity or fragment — the host stays resumed, so `onPause`/`onStop`/`setUserVisibleHint`/`onPageSelected` none fire on that path. Any save logic hung on page-change or pause/stop callbacks is therefore bypassed exactly when the user opens the picker, which matches the reported intermittency (UPDATE runs on swipe-away, never runs on picker-open). The reliable hooks for dialog-open are: explicit save call before `dialog.show()`, the dialog's dismiss/callback delivering the picked value, or observing the dialog result — never a lifecycle callback.

### Cited Findings
- `Fragment.onPause()` is "called when the fragment is no longer resumed" — i.e. only when the fragment actually leaves the resumed state ([Source](https://developer.android.com/reference/kotlin/androidx/navigation/dynamicfeatures/fragment/DynamicNavHostFragment)). A dialog appearing over the activity does not move the host activity out of resumed: the activity lifecycle guide's foreground/background transitions are driven by the activity leaving the foreground (home, recents, another full-screen activity, lock), and a dialog window keeps the host interactive-visible ([Source](https://developer.android.com/guide/components/activities/activity-lifecycle)).
- `DialogFragment.show()` adds the dialog as a separate window on top of the same activity; the underlying fragment receives no lifecycle event (at most `onSaveInstanceState` ordering constraints around `dismiss()` after state save — "dismiss can be called safely after onSaveInstanceState", implying dialogs and saved-state interleave without pausing the host) ([Source](https://developer.android.com/reference/com/google/android/material/bottomsheet/BottomSheetDialogFragment)).
- "Saved state APIs only save data when the Activity is stopped. Any data written to these APIs between lifecycle states will defer the save operation until the next stopped lifecycle event" — so even `onSaveInstanceState`-based persistence would defer past a dialog-open; only an explicit write at dialog-open/dismiss time persists promptly ([Source](https://developer.android.com/topic/libraries/architecture/saving-states)).
- For `ViewPager`/`ViewPager2`, page-change visibility is delivered via `OnPageChangeCallback.onPageSelected` / the adapter's primary-item / `FragmentTransaction.setMaxLifecycle` (ViewPager2) or `setUserVisibleHint` (legacy ViewPager + `FragmentStatePagerAdapter`) — all of which fire only on actual page switches, never when a dialog opens above the current page ([Source](https://developer.android.com/reference/androidx/viewpager2/widget/ViewPager2.OnPageChangeCallback); [Source](https://developer.android.com/reference/androidx/viewpager2/adapter/FragmentStateAdapter)).

### Inferences
- Probable defect shape: body save is wired to a page-change/pause trigger (or to "picker confirm returns → save", where the confirm path that issues INSERT for new notes has no symmetric UPDATE for existing notes). When the picker opens, no lifecycle/page callback fires, so the UPDATE is skipped; when the user instead swipes or leaves, the trigger fires and the body persists — hence intermittent.
- Correct save-trigger contract for this editor: (1) flush `getText()` → model → UPDATE **synchronously before** `dialog.show()` (or in the picker's `onDismiss`/result callback for value-dependent saves); (2) keep `onPause`/page-change save as the backstop for non-dialog exits; (3) never rely on `onPause`/`onStop`/`onPageSelected`/`setUserVisibleHint` to cover dialog-open, because the platform guarantees they will not fire there.
- Concretely for verification: drive two flows — picker-open-then-confirm and swipe-away — and assert a DB UPDATE in both; today only the second is expected to pass.

### Gaps
- Whether the app uses legacy `ViewPager`+`FragmentStatePagerAdapter` (`setUserVisibleHint`, deprecated, fires on page change only) or `ViewPager2`+`FragmentStateAdapter` (`setMaxLifecycle`, same page-change-only semantics for this question) was not confirmed from source (APK classes only); the dialog-open conclusion holds for both, but the exact page-change hook name differs.
- No retrieved snippet explicitly states "DialogFragment does not pause the host" verbatim; it follows from the activity-lifecycle foreground definition plus DialogFragment's separate-window design, both cited. If the report needs a single smoking-gun sentence, that sentence was not found in retrieval.
